# AGENTS.md

## What this is
Room Planner is a client-only web app with **three small runtime dependencies** (`preact`, `@preact/signals` and the `@preact/signals-core` it builds on, all bundled in). What ships is one self-contained HTML file you can open off disk — that deployment model is not negotiable — but it is *built* rather than hand-maintained:

```sh
npm install && npx playwright install chromium   # once
npm run dev        # Vite dev server on http://127.0.0.1:5173, HMR on save
npm run build      # -> dist/index.html, one file, everything inlined
npm test           # 124 Vitest + 26 Playwright, ~45s
npm run lint       # ESLint (correctness + import boundaries), then npm run cycles
npm run typecheck  # tsc over the JSDoc types: kernel/, ui-kit/ and every feature API strict
```

`dist/` is **never committed** — a generated 322 kB file touched by every PR conflicts on every merge, which is the exact problem the module split exists to solve. It is gitignored, and CI fails if it is ever tracked. Both workflows live in [`.github/workflows/`](.github/workflows): `ci.yml` runs lint, unit, build and the browser suite on every pull request; `pages.yml` builds and publishes `dist/` to GitHub Pages on every push to `main`. Review routing is in [`.github/CODEOWNERS`](.github/CODEOWNERS).

Two consequences worth knowing before you touch anything:

- **`index.html`'s `<script>` blocks are `type="module"`** (Vite entry points; each HTML partial carries one too), so the source file does **not** run from `file://` — module scripts are fetched under CORS rules an opaque `file://` origin cannot satisfy. Open `dist/index.html` for that, which is what actually ships.
- **All tooling is a devDependency.** A runtime `dependency` must be small, must bundle into the single `dist/index.html` (so the `file://` contract is untouched), and needs a stated reason. Today there are three, one family:
  - `@preact/signals-core` (~4 kB min) — the reactive core the side panels and the canvas subscribe through; see *Committing a change* below. `kernel/` imports only this one.
  - `preact` (~11 kB min, plus ~4 kB of hooks) — the side panels' components (`.jsx`, compiled with Preact's automatic JSX runtime); it diffs what a panel shows against what is on screen, so a list keeps its rows, its focus and its scroll position across a repaint, which a re-set `innerHTML` cannot. React would be the same idea at four times the size.
  - `@preact/signals` (~5 kB min) — Preact's binding to that same core (it imports `@preact/signals-core`, deduplicated to one copy in the bundle): a component that reads `signal.value` while rendering re-renders when it changes, so a component subscribes exactly the way an `effect` does. It installs itself as Preact options hooks when imported, which `ui-kit/component.js` (the one function every component is mounted through) does.

## How the source is laid out

**[index.html](index.html)** is **112 lines** and is a shell: seven lines of `<head>`, a `<link>` to the stylesheet, seven `<!-- @include -->` directives holding the page structure together, and one `<script type="module">` holding **twelve** listener registrations and the two calls that start `edgePanTick()` and `boot()`. Everything else — **143 JS modules**, **16 JSX component modules**, **15 SCSS partials** and **7 HTML partials** — lives under `src/`, in four kinds of place:

```
src/kernel/            the document and its rules; no DOM
src/ui-kit/            generic UI every feature builds with
src/features/<name>/   one feature: its commands, panels, layers, tools, and its own model
src/app/               composition: boot, the canvas parts list, global shortcuts, the panes
```

- **`src/kernel/`** — the state (`state.js`: `S`, `setS`; `selection.js`: the selection signals), committing a change (**`tx.js`**: `transact`/`preview` — see *Committing a change*), the revision signals views subscribe to (**`signals.js`**, which also carries `report()`/`notice`, how the kernel tells the person something), undo (`history.js`), persistence (`store.js`, `migrate.js`), the primitives (`units`, `geometry`, `color`, `ids`), and under **`kernel/model/`** the domain model several features share: `walls`, `openings`, `validity`, `floor-place`, `floor-space`, `open-state`, `item-folders`. Model code a single feature owns lives in that feature, not here. It would still make sense with no screen attached.
- **`src/ui-kit/`** — `dom.js` (`$`, `esc`, `svgI`), `modal.js` (+ `modal.html`, `modal-bind.js`), `menu.js`, `inline-edit.js`, `dnd.js`, `tag-input.js`, `panels.js` (section and pane collapsing, list helpers), `flash.js`, `component.js` (`mountComponent`) and `parts.jsx` (the pieces components are built from, `Field` among them — see *Rendering*), and the control styles (`_buttons`, `_inputs`, `_modal`, `_menus`, `_dnd`).
- **`src/features/`** — fourteen of them, each with an **`index.js` that is its public API**:
  - `canvas` — the camera (`view.js`, `camera.js`), the compositor (`draw.js`) and palette (`paint.js`), the pointer dispatcher (`interaction.js`) and pan tool, the drawing tools' shared state, snapping and picking (`snap.js`), the View settings, and the layers no one feature owns (stage, alignment guides, readout). See *The canvas*.
  - `mode` — `setMode`, `activateLayout`, the mode buttons and undo/redo buttons.
  - `walls`, `openings`, `room` — Room mode, split by part: walls/corners/pillars/interior walls (lists, props, wall dialog, the interior-wall tool, their layers); doors and windows (list, props, dialog, layer); the room itself (properties, the Selection panel that dispatches to the part's own props renderer, the custom-outline and split tools, the Room-mode tool, the floor and handle layers).
  - `furniture` — the item list, the Selection panel, the Furniture-mode tool, the item layers.
  - `floors` — Floor mode: arranging and merging rooms, its panels, tool and layers.
  - `measure`, `walkpaths` — each a model, a layer (and for Measure a tool, its state and the bar).
  - `layouts` — the folder/floor/room tree and its row menus.
  - `library` — the Library/Marketplace page (`#paneLibrary`: its partial, `page.jsx` and the views under it, `_library.scss`) and the item editor `itemDialog`, which the furniture list shares.
  - `marketplace` — the catalogue sources: subscriptions and ad hoc listings, fetched, validated, cached.
  - `io` — export, import and the pickers they share. `blueprint` — the photo-to-rooms wizard (`flow.js` states the stage order; `_blueprint.scss`).
- **`src/app/`** — `boot.js` (`boot()`, exported and called from `index.html`; it mounts every view), `canvas-setup.js` (the list of every layer and tool), `shortcuts.js` (the document keydown/keyup routing), `html/` (the header, the stage and the two side panes) with `bind/` (the header's and the stage's listeners: those partials end in a module script that calls their `bind*()`), `slots.js` (fills the side panes' sections — see *Side panels*), and `styles/` (`main.scss`, the `@use` manifest that states the cascade order, plus the page-level partials and `_tokens.scss`).

**The boundaries are enforced, not described.** `eslint.config.js`'s `rp/boundaries` rule resolves every relative import: `kernel/` imports only `kernel/` (and `document` is off limits there); `ui-kit/` imports `kernel/` and `ui-kit/`; a feature imports `kernel/`, `ui-kit/`, its own files directly, and **other features only through their `index.js`** — never `app/`, never its own `index.js`; `app/` imports anything, features through `index.js` or, for what only the shell needs, a feature's `host.js` (`features/canvas/host.js`: the stage's event handlers, the layer and tool registry, the canvas's mounts), which no feature may import. And **there are no import cycles**: `npm run lint` ends with `npm run cycles`, which fails on any. So the features form a DAG (canvas at the bottom; mode above it; walls → openings; room → walls; floors → room, furniture, io; layouts → floors, room, blueprint; library → io, marketplace; furniture → library). When a feature needs one that needs it back, one of them is in the wrong place, or the call wants to be a signal the other side subscribes to — see how tools are stopped by kind and how the kernel reports a refused edit.

### Adding things

- **A feature**: `src/features/<name>/` with an `index.js` that exports what others may use (and a header saying what the feature is), plus a line in `.github/CODEOWNERS`. Its pane sections are filled from its `sections` map (add the feature to `FEATURES` in `app/slots.js`), its layers and tools come from `app/canvas-setup.js`; its partial, if it owns a whole pane, is an `@include` in `index.html` and its SCSS an `@use` in `app/styles/main.scss`, at the point in the cascade it belongs.
- **A layer**: a `*-layer.js` module in the feature that owns the concern, exporting `{id, z, scene?, deps?, draw, hitTest?}`; export it from the feature's `index.js` and add it to `LAYERS` in `app/canvas-setup.js`. No existing layer changes.
- **A tool**: a `*-tool.js` module in its feature (gesture state lives in it), exported through `index.js` and added to `TOOLS` in `app/canvas-setup.js` at its priority. If it is switched on and off, give it `stop()` and have its start command call `stopOtherTools(id)`; `modes` if it may not survive a mode change, `reset()` if it holds picks that belong to one room. Nothing outside the tools names a tool.
- **A panel**: a component (`.jsx`, strict) in the feature that owns it, reading the signals it shows while it renders; an entry in that feature's `sections` map (`{key(el){ mountComponent(el, <MySection/>); }}`, exported from its `index.js`); and one `<section data-sec="key" class="for-…">` line in the pane partial (`app/html/pane-left.html` or `pane-right.html`) where it sits, plus its key in the narrow `order` list in `app/styles/_narrow.scss`. Nothing else in `app/` changes. Commands commit through `transact()` and never call a render function.

### Moving code between modules

The split is done, but code still moves, and the two findings that cost the most to learn are worth having before you start.

**When a big function looks unmovable, check whether what is really stuck is the mutable state it reads, not the code.** `draw()` was called an unbisectable 1,500-line component; it moved as an ordinary 766-line commit once the state it reads had moved out ahead of it. **Mutable shared state belongs in leaf modules that import nothing but `kernel/signals.js`** — `kernel/state.js` (`S`), `kernel/selection.js` (the selection signals), `features/canvas/interaction-state.js`, `features/measure/measure-state.js` (drawing-tool and measure-tool signals). `features/library/nav.js` holds the Library page's browsing state with the two moves that change it. A drag's own state is the exception: it lives in the tool that runs it (its `*-tool.js`), because nothing else reads it. Keep it that way.

**That does not dissolve every knot, so check which kind you have.** The Plan side panels and the Library UI were once one strongly-connected component of 49 names, and its six edges were plain function calls rather than shared state — no setter breaks that, and it had to move whole, in one commit of 1,326 lines into 15 modules. Ask the question explicitly (state, or calls?) rather than assuming the `draw()` answer.

**A move is a move.** Byte-identical lines, no renames, no reordering, no reformatting, no fixes folded in; `git blame` survives a pure move and that history is what settles an argument later. A behaviour change — a `setX(v)` setter, say — goes in its own commit and says so in the message. Bugs you spot go in `BACKLOG.md`.

**Four more rules carry forward, and all four have drawn blood.**

1. **No import cycles, and no edge that drags a top-level read into one.** `features/canvas/view.js` runs `const cv=$('cv'), ctx=cv.getContext('2d')` at module-eval time; inside a cycle, a module like that can be evaluated before the one that defines `$`, and the app dies at boot. The graph has none now and `npm run cycles` (part of `npm run lint`) fails on the first one, so check any new edge with it, not by eye. The ways cycles were broken are the patterns to reuse: move the shared piece down into a leaf (`ui-kit/dom.js`, `features/library/preview.js`), state an order once in a module the stages do not import (`features/blueprint/flow.js`), or turn the back edge into a signal (`features/library/nav.js`'s `navChanged()`, the kernel's `report()`).
2. **`test/epilogue.js` is not linted.** `__rp` names a binding that must still be in `index.html`'s scope; when the last reader moves out, you get a bare `ReferenceError` at module evaluation, with a green build and a green browser. Where a name has moved, the epilogue **imports** it rather than `index.html` importing it back. Worse are the `GLOBALS` entries, which assign inside a `try/catch` and so fail *silently* and late. There is a standing audit for both; see `test/README.md`.
3. **A listener is registered from inside a function, never at import time.** A module that calls `addEventListener` while it is being evaluated introduces a top-level side effect, and binds at import-hoist time rather than at the point in the document its markup occupies. So each partial that has listeners exports a `bind*()` from a module beside it (`src/app/bind/`, `ui-kit/modal-bind.js`) and the partial calls it, the Library's partial renders its page component (`mountLibraryPage`), and a pane section's fill binds its own (a component's listeners are props on its elements) — the same trade `app/boot.js` and `edgePanTick()` already make. Two consequences worth knowing:

   **Registration order decides nothing between listeners on different elements.** It decides everything between listeners on the *same* element in the same phase. Every element with more than one listener — `cv`, `mo` — belongs to exactly one partial (a component's listeners are props on its own elements, so they have no order to keep), so no such group is split; keep each group's internal order when you touch one. `document` is the exception and the reason the remaining handlers are in `index.html`: several unrelated features listen to it, and the two bubble-phase `keydown`s there are order-dependent.

   **A body of any size belongs in the module that owns the concern**, where a unit test can reach it. A body that moves into the module owning a binding it writes stops needing that binding's `setX(v)` shim, which is a behaviour-free simplification worth taking; do not go hunting for the others.

   **Import paths inside a partial resolve against `index.html`, not the partial's own folder**, because `rp:html-includes` splices the text before Vite parses the document. So the specifier is `'./src/app/bind/foo.js'`. It looks wrong; it is not.

4. **ESLint cannot check a name against its module.** `import {sizeLabel} from '../measure/index.js'` passes the boundary rule and `no-undef` even though `sizeLabel` is exported by `features/library/items.js` — `no-undef` sees the name as declared by the import either way, and the boundary rule checks where an import points, not what it names. A real name behind the wrong file is invisible to lint and is found only by running the suite. Verify the *module*, not just the name.

**There are no top-level side effects anywhere in `src/`.** Every module defines and exports; nothing runs at import time. The one exception is a package's, not ours: `ui-kit/component.js` imports `@preact/signals`, which installs Preact option hooks when it is evaluated (see *What this is*, the `@preact/signals` entry) — harmless at any point before the first component renders, which is why it is imported by the one function every component mounts through. **`src/app/boot.js` exports `boot()` and `index.html` calls it**, at the exact line its IIFE occupied. That is deliberate and worth not undoing — importing a `app/boot.js` that called `boot()` itself would run boot *before* `index.html`'s listener registrations, since imports hoist and evaluate ahead of the importing module's body. It would happen to work, because `boot()` suspends on its first `await`, but nothing in the suite would catch it if that stopped being true. The `edgePanTick` rAF loop is the same shape, exported from `features/canvas/interaction.js`.

**Styles are SCSS, and `src/app/styles/main.scss` is where the cascade order is stated.** The partials are plain CSS cut on the banners that were already in the `<style>` block, so `@use` order *is* source order and later rules still win ties on equal specificity — put a rule where it belongs in the sequence, not at the end. Nothing is nested and nothing uses `@extend`; if you nest, the cap is two levels plus `&` modifiers. **The design tokens are CSS custom properties and must stay that way** — dark mode re-declares all 24 under `@media (prefers-color-scheme:dark)`, and a Sass `$variable` is compile-time and cannot cascade, so converting one deletes dark mode with every test still green. See [DESIGN.md](DESIGN.md) §3.2.

**The static markup lives in HTML partials beside the code that binds them (`src/app/html/`, `src/features/library/pane-library.html`, `src/ui-kit/modal.html`), behind `<!-- @include src/…/foo.html -->`.** A local Vite plugin, `rp:html-includes` in [vite.config.js](vite.config.js), substitutes each directive in `transformIndexHtml`. It runs first in the chain (`enforce: 'pre'`, `order: 'pre'`), so the epilogue, `rp:classic-script-tag` and `vite-plugin-singlefile` all see one whole document. **It is a textual splice and must stay one** — the shell is static markup the browser parses before any script runs, which is what the bind functions assume when they look up `#paneRoom` or `#paneLibrary`. The side panes' sections are the exception by design: the partial holds each as an empty `<section data-sec>`, and its feature fills it at boot (`app/slots.js`) before anything reads it. `test/unit-setup.js` carries the same substitution, because it reads `index.html` off disk instead of through Vite — **keep the two in step**, or the jsdom shell has no `#cv` and the app dies at module evaluation with a wall of red unit tests, a green build and a green browser. It strips **every** `<script>` block by regex; it used to cut from the first `<script` to the last `</script>`, which was exact while there was one and silently deleted every pane between the header partial's script and the shell's once there were several. It now asserts one id per partial afterwards and names the pane that went missing, because that failure otherwise surfaces as a null dereference three imports deep.

The header nav (`#navSeg`) switches between three **places**: **Plan** (the canvas + side panels), **Library** and **Marketplace** (a full-width library UI, `#paneLibrary`, that swaps in for `<main>` when active — see `isCanvasMode()`/`applyLayoutMode()`). Inside Plan, the **Room | Furniture** mode switch (`#modeSeg`) sits on the canvas itself. `S.mode` is one of `'room'|'furniture'|'inventory'|'marketplace'`; `S.planMode` remembers which canvas mode to return to from the header. `setMode()` (**[src/features/mode/mode.js](src/features/mode/mode.js)**) toggles between the canvas layout and the library layout; it is a prefs commit, so the Library page (a component on the settings, the library and `navRev`) paints on arrival.

**Design rules live in [DESIGN.md](DESIGN.md)** — tokens, components, wording ("item", "Library", never "thing"/"inventory" in UI copy) and a review checklist. Read it before adding UI; all colours, sizes, radii and shadows come from the CSS custom properties in [`src/app/styles/_tokens.scss`](src/app/styles/_tokens.scss), never literals.

To preview: `npm run dev`, or `npm run build && open dist/index.html` to check the shipped artifact.

## Verifying changes
`npm test` is the gate, and CI (`.github/workflows/ci.yml`) runs the same commands on every pull request, plus a check that nothing under `dist/` is tracked. Read [`test/README.md`](test/README.md) before touching anything under `test/` — it opens with the rule that shapes the directory: **test code stays under 20% of the codebase, and ideally under 10%** (it is 1,702 lines against 15,305 today). The characterization baseline that guarded the module split has been removed now that the split has landed; what is left is a permanent suite, and every addition to it needs an argument about what it catches that nothing else does.

- `npm run test:unit` (~2s) — Vitest + jsdom: units, `migrate()` goldens and import/export round-trips, imported straight out of `src/`, plus the build-pipeline tests.
- `npm run test:e2e` (~40s) — builds, then Playwright + Chromium against **both** the dev server and `dist/index.html`, sharing one set of goldens so the build cannot move a coordinate unnoticed. Covers the smoke path, the blueprint geometry golden, two pointer gestures and the `file://` deployment contract.
- **What it does NOT cover** is written down in `test/README.md` — the side panels, the canvas's pixels, most pointer interaction and the marketplace. A break in any of those turns nothing red, so exercise them by hand.
- `npm run typecheck` — `tsc` over the JSDoc types, no emit (`scripts/typecheck.mjs`, both configs explained in `tsconfig.json`). Every module is checked at the default level; a module whose first line is `// @ts-check` is held to `strict`, and `kernel/`, `ui-kit/`, every feature's `index.js` (and `host.js`), every module those re-export from, and every `.jsx` component must be. The script lists the modules that are not yet strict — the ratchet; making one strict is adding the pragma and fixing what it reports. Shared types are declarations: `src/kernel/types.d.ts` (the saved document, `transact()`'s scopes) and `src/features/canvas/types.d.ts` (`Layer`, `Tool`); a layer or tool says which it is with `/** @satisfies {import('../canvas/types.js').Layer} */`. A change to the saved shape updates `kernel/types.d.ts` alongside its `migrate()` step. CI runs it; it is not part of `npm test` or `npm run lint`.
- `npm run lint` — ESLint: correctness rules plus `rp/boundaries` (see *How the source is laid out*), then `npm run cycles`, which fails on any import cycle. No Prettier and no formatting rules, deliberately: the dense style here is a decision, and reformatting 10k lines would destroy `git blame`. `no-undef` is the rule that earns its keep.

Still worth doing by hand for anything visual: `npm run dev` and exercise the area you changed (draw/resize a room, place furniture, undo/redo, switch units).

## Architecture
- **Units** (**[src/kernel/units.js](src/kernel/units.js)**, imported at the top of `<script>`): everything is stored internally in **millimetres**; `parseLen`/`fmtLen` convert to/from the user's display unit (ft+in, in, cm, mm, m). Don't introduce a second unit system — always store mm and format at render time. Geometry helpers are in **[src/kernel/geometry.js](src/kernel/geometry.js)**.
- **State** (**[src/kernel/state.js](src/kernel/state.js)**): a single global `S` object holds `layouts` (rooms), `inventory` (furniture items), `folders`, and UI prefs (unit, snap, mode). Each layout's room is a closed polygon: `room.points = [[x,y], ...]` (clockwise, mm).
- **Persistence**: `Store` wraps `window.storage` (if present) or falls back to `localStorage`. `save()` debounces writes. `migrate(st)` (**[src/kernel/migrate.js](src/kernel/migrate.js)**, *not* `store.js` — see the cycle rule above) upgrades older saved-state shapes on load — **when changing the shape of `S`, add a migration step here** rather than assuming fresh state. `S` itself is reassigned wholesale on load and on import; it lives in a module now and you cannot assign to an imported binding, so every such write goes through `setS(v)` (**[src/kernel/state.js](src/kernel/state.js)**), never a bare `S = …`.
- **Inventory tab**: organizes the same `S.inventory` used by Furniture mode, adding `item.folderId`/`item.manualTags` alongside the existing `item.tags` (the folder-inherited half — see `applyTags`/`reconcileTags`), plus top-level `S.itemFolders` (a folder tree with `tags:[]` materialized onto everything filed under it). Browsing is a folder tree (`lib-tree.jsx`) + grid (`lib-grid.jsx`); editing an item's shape/color/count/etc. reuses the *same* `itemDialog(id)` modal (**[src/features/library/item-dialog.js](src/features/library/item-dialog.js)**) as Furniture mode's "Add a thing" — the Inventory tab doesn't have its own item editor. Its own Export (`exportLibraryDialog`/`exportLibFolder`/`exportLibItems`) writes `{app, version, exported, inventory}`, the same shape `ITEM_SCHEMA.md` documents, so it round-trips through the app's main Import.
- **Marketplace tab**: two independent sources, both landing on the same `addMarketItemToInventory()` collision flow (see **Marketplaces** below):
  - **Subscriptions** (`S.marketSubs`): live `market.json` URLs per **[MARKET_SCHEMA.md](MARKET_SCHEMA.md)**. `subscribeMarket()`/`reloadMarketSub()`/`removeMarketSub()`/`fetchMarketItem()` fetch and validate `app`/`version` on every manifest, index shard, and item file. `marketIndexCache`/`marketItemCache` are in-memory `Map`s, never persisted — only the subscription record itself (`{id,url,name,version,itemURL}`) is saved.
  - Clicking a subscribed item opens `renderMarketItemPreview()` as a dialog (the views are `market-views.jsx`) (its "Add to library" defers `addMarketItemToInventory()` with `setTimeout`, so a collision dialog can open after the preview closes).
  - **Ad hoc listings** (`S.marketListings`/`S.marketFolders`): the older upload/paste-JSON/flat-link path, for sharing a one-off bundle without hosting a repo. Unrelated to the schema above.
- **Committing a change** (**[src/kernel/tx.js](src/kernel/tx.js)**): every edit to saved state goes through `transact(scope, fn, opts?)`, scope one of `room | furn | floor | lib | prefs | project`. It runs `fn()`, records the matching undo stack (room/furn/floor; the others have none; `{history:false}` skips it), bumps the layout revision when the scope can change what the validity and walk-path caches read (room/furn/lib/project), `save()`s, and bumps the revision signal of each scope it touched (`rev[scope]` in **[src/kernel/signals.js](src/kernel/signals.js)**) plus `planRev`, the canvas's, unless the edit passed `{canvas:false}` because the plan does not show it (list filters, collapsed sections) — all in one signals `batch`, so no view runs halfway through an edit. Nested calls commit once, at the outermost. A gesture's pointermove frames use `preview(scope, fn)` (no history, no save) and its pointerup calls `transact` once, so one gesture is one undo step. **Don't call `save()`, `commitRoom/Furn/Floor()`, `draw()` or any `render*()` after an edit, and don't name a panel**: every view is an effect on the signals it shows (see *Rendering*) and repaints itself. A bare `draw()` is allowed only for a synchronous paint something needs at once (`the Measure tool's press, whose label hit boxes come out of the draw), for state that is not a signal (the camera, a gesture object mutated in place mid-drag), or `savePlanImage`'s light-palette capture.
- **Undo/redo**: room edits and furniture edits have **separate** history stacks (`roomHist`/`furnHist`), keyed per-layout, plus one per floor for arrangements; `transact` is what writes to them. Replaying a snapshot bumps that scope's revision signal like a commit does, and `histRev` moves whenever a stack does, which is what the undo/redo buttons subscribe to.
- **Rendering**: the canvas is described under *The canvas* below; it is an effect (`mountCanvas`) that schedules one draw for the next frame whenever a commit or a signal some layer shows changes. The side panes' lists are **Preact components** (`.jsx`): the Rooms tree (**[layouts/tree-section.jsx](src/features/layouts/tree-section.jsx)**), Items and Stock (**[furniture/items-list.jsx](src/features/furniture/items-list.jsx)**), Walls and Pillars & interior walls (**[walls/walls-list.jsx](src/features/walls/walls-list.jsx)**), Doors & windows (**[openings/openings-list.jsx](src/features/openings/openings-list.jsx)**). A component reads the signals it shows while it renders — `rev.room.value`, `pref('unit')`, the selection — and `@preact/signals` re-renders it when one changes, exactly as an effect re-runs; Preact patches the elements already on screen, so rows are keyed, listeners are props on the elements they belong to, and a field being typed in (the search box, a rename box) is the same element afterwards with its text, caret and focus intact. A row being renamed is a signal the row renders a `RenameField` for (`ui-kit/parts.jsx`), not a DOM node swapped under Preact; a drag in flight is component state, so its marks render like anything else. So are the Properties pane's sections — the Selection panels (**[room/sections.jsx](src/features/room/sections.jsx)** with the part views in **[walls/wall-props.jsx](src/features/walls/wall-props.jsx)** and **[openings/opening-props.jsx](src/features/openings/opening-props.jsx)**, **[furniture/selection-section.jsx](src/features/furniture/selection-section.jsx)**, **[floors/sections.jsx](src/features/floors/sections.jsx)**), Room, Floor and View (**[canvas/sections.jsx](src/features/canvas/sections.jsx)**) — and the Library/Marketplace page (**[library/page.jsx](src/features/library/page.jsx)**). **A component that reads a signal is re-rendered by those signals, and by its parent only when its props change** (`@preact/signals` skips it otherwise), so a component reads every signal it shows, or none and takes what it shows as props from one that does. **Form boxes**: a box over a model value is a `Field` (`ui-kit/parts.jsx`; `Select` and `Check` for the others). While it has focus and something has been typed in it, it is the user's — a repaint, even one its own `onInput` caused (the floor colour's hex box commits every keystroke and keeps a partial `#12`), leaves its text, caret and selection alone; when it commits (Enter, or leaving an edited box) it hands the text to `onCommit`, which commits through `transact()` or refuses, and then shows the model's value again, selected if it still has focus — so a refused edit (a wall's Direction of 180°, an item's From left of 99 m) snaps back. Because the element survives the commit, Tab goes on to the next box. A form that reads several boxes to commit one passes the others as shown (formatted), so a commit rounds them the way reading the boxes did. To add a panel, write a component (see *Adding things*), and never call it from a command. Signals (`kernel/signals.js`, `@preact/signals-core`) are read with `.value` and written by assigning `.value`; Set-valued ones are replaced, never mutated in place. The Library's browsing state (`features/library/nav.js`) is not a signal, but browsing calls `navChanged()`, which bumps the `navRev` signal the page reads; library *edits* commit and the page follows. While a Plan mode is showing, the page hands back what it last rendered, so it neither repaints nor fetches while hidden.
- **The canvas** (**[src/features/canvas/](src/features/canvas/)**). The camera is **[view.js](src/features/canvas/view.js)** (`cv`, `ctx`, `view`, `sx`/`sy`/`wx`/`wy`, `snapPt`), a leaf every layer and tool imports. **Layers** draw: `draw()` (**[draw.js](src/features/canvas/draw.js)**, the compositor) paints every registered layer in `z` order — the stage layer at z 0 clears the canvas — immediate mode, each between `ctx.save()`/`ctx.restore()`. A layer is `{id, z, scene?, deps?(), draw(ctx, view, frame), hitTest?()}` in its own `*-layer.js` module, in the feature that owns what it draws: `scene` is `'room'` (the active room — Room and Furniture modes) or `'floor'` (Floor mode, every room at once), `deps()` reads the signals it shows so the canvas effect repaints when they change, and `frame` carries what several layers share (`C` = `PAL()`; `bad`/`openBad` in the room scene; `fl`, `members`, `depths`, `empty` in the floor scene). The z order is the plan's paint order — stage 0, floor/underlay 10–20, walk paths 30, walls 40, interior walls 50, pillars 60, openings 70, open regions 80, items 90, labels 100, guides 110, handles 120–125, measurements 130, tool overlays 140–170, readout 1000 — so a new layer picks a z between the two it belongs between. **Tools** handle gestures: `{id, active(), onDown, onMove?, onUp?, onCancel?, onHover?, onCursor?, onLeave?, onKey?, autoPan?, cursor?, overlay?}` in its own `*-tool.js` module in its feature (the header of **[interaction.js](src/features/canvas/interaction.js)**, the dispatcher, spells each one out). The active tool is the first registered one whose `active()` holds — a drawing tool or Measure while one is on, else the canvas mode's own — and Space hands a press to the pan tool. `onDown` returns the tool that holds the pointer until it comes up (itself, `startPan()` for a press on nothing, or null); that tool gets the moves and the release, or `onCancel` on Escape, and keeps the gesture's state in its own module. A tool's frames call `preview()` and its release calls `transact()` once, so one gesture is one undo step. Its `overlay` is a layer that draws the gesture. A tool that is switched on and off (the drawing tools, Measure) has a `stop()`, and its start command calls `stopOtherTools(id)` first, so only one is ever on and a new one needs no edit to the others; code outside the tools ends them by kind — `stopDrawing()` (every tool with `onCursor`), `stopToolsFor(mode)` (a tool's own `modes`), `resetTools()` (a tool's `reset`, on a room change) — never by name. **To add a layer or a tool**, write the module, export it from its feature's `index.js` and add it to the list in **[app/canvas-setup.js](src/app/canvas-setup.js)**, whose `setupCanvas()` `boot()` calls; nothing registers at import time, and no existing layer or tool changes. Keys the active tool does not claim go on to `app/shortcuts.js`, which also holds the mode tools' keys (Delete, arrows, `[`/`]`) because those run several features' commands.
- **Side panels**: left `#paneRoom` ("Plan") holds *lists* — rooms, then the items (Furniture mode) or walls/doors/structure (Room mode); right `#paneStuff` ("Properties") holds the *selection* first, then room properties / stock, then View settings. **Each section is a slot**: the pane partial lists it as an empty `<section data-sec="…" class="for-…">` (its place, which mode shows it, and the key its collapsed state and narrow order go by), and the feature that owns it fills it — its `index.js` exports `sections`, a map from that key to a fill function (`(el) => void`, typed in `ui-kit/component.js`), and `fillSlots()` (**[app/slots.js](src/app/slots.js)**) calls each at boot, failing loudly on a section nobody fills or a key with no section. Sections meant for one mode carry `for-room` or `for-furn` and are hidden by `body[data-mode]` (set in `renderMode()`). Each `.pane` is a `.pane-head` rail plus a `.pane-body`; `applyPanes()` drives `S.leftOpen`/`S.rightOpen` and the `lc`/`rc` classes on `<main>`. Collapsing is desktop-only: under 900px the panes become `display:contents`, the canvas is sticky on top, and sections stack in the order set by `section[data-sec=…]{order}` in the narrow media query. Every `section` has a `.sec-head` (an `h2` that toggles collapse, plus optional `.sec-act` buttons such as the `+` that adds to that list — `SecHead`/`ActButton` in `ui-kit/parts.jsx`) and a `data-sec` key persisted in `S.secClosed` — new sections need both. The toggling stays one delegated listener in `index.html` and `applySections()` (`ui-kit/panels.js`), which runs after the fills.
- **Icons, dialogs, toasts** (**[src/ui-kit/modal.js](src/ui-kit/modal.js)**, **[src/ui-kit/flash.js](src/ui-kit/flash.js)**): icons are `<symbol>`s in the sprite at the top of `<body>`; render them with `svgI('name')` (no emoji). `openModal(title, html, okLabel, onOk, onMount, {danger:true})` styles a destructive action; `askConfirm()` always does. `flash()`/`libFlash()` stay up for `readTime(msg)`. `$(id)` and `esc(s)` — the two helpers every render path uses — are exported from `src/ui-kit/modal.js` and `src/ui-kit/panels.js` respectively.
- **Canvas colours** (**[src/features/canvas/paint.js](src/features/canvas/paint.js)**): layers and tool overlays read colours from `PAL()` (`CANVAS.light`/`CANVAS.dark`, following `prefers-color-scheme`), never literals. Only stage-side colours (background, walls, labels) differ in dark mode; selection/handles/warnings sit on the user's floor colour and keep light values. `savePlanImage()` (reached from the Export dialog) forces the light palette.
- **Double-click**: a wall opens `wallDialog(i)` — from the plan (canvas `dblclick` → `pickRoom`, Room mode only) or from a row in the Walls list. It is the same length/direction pair as the Selected panel, and it leans on `setWallLen`/`setWallAngle` returning false when `tryRoomEdit` rolls the change back, in which case the modal stays open over the flash message.
- **Row menus** (**[src/ui-kit/menu.js](src/ui-kit/menu.js)**, **[src/ui-kit/inline-edit.js](src/ui-kit/inline-edit.js)**): the `⋯` buttons (`MoreButton` in `ui-kit/parts.jsx`) open an anchored `openMenu(anchor, actions, title)` popup, not the modal. Actions that need more than one click (rename with a box, pick a folder, confirm a delete) open the modal *from* the menu. Renaming in place is a `RenameField` in a component's row; because a row's single click does something, click handlers on those rows go through `singleClick()`/`cancelSingleClick()` so a second click can become a double-click instead.
- **Reordering** (**[src/ui-kit/dnd.js](src/ui-kit/dnd.js)**): the layout tree and the inventory list use HTML5 drag-and-drop. `moveBefore(arr, movedId, targetId, after)` does the splice — folders and rooms live in separate arrays (`S.folders`, `S.layouts`), so a drop only reorders against its own kind and otherwise just reparents. `folderDescendant()` is the cycle guard.
- **Inventory scope**: `S.invScope` (`project` | `folder` | `room`, see `INV_SCOPES`) decides which rooms `usedCount()` counts, via `scopeLayouts()`. `folder` means the rooms sitting *directly* in the active room's folder — a subfolder is its own pool and never draws on the folder above it.
- **Modal dialogs** (**[src/ui-kit/modal.js](src/ui-kit/modal.js)**): implemented as a plain `<div>` (`#modal`), never `<dialog>` or `<form>` — the code comment explains both are blocked in sandboxed iframes this app may run in. Keep using `openModal()`/`closeModal()`.
- **Ids**: an inventory item's id is user-editable (Advanced, inside the edit dialog), so it is held to a URL/S3-safe character set by `idProblem()` — letters, digits, `! - _ . * ' ( )`, and `/` between path parts (no leading, trailing, or doubled slash). A slash reads like an S3 key: `ikea/kallax/4x2` and `ikea/kallax/2x4` sit in the same folder — both the Inventory tab's own folder tree (`rehomeItemId()` keeps an item's id filed under its folder path) and a subscribed marketplace's browse view (`marketPathChildren()` derives folders straight from id path segments, no separate folder list) use this convention. `retagItem()` is the only sanctioned way to change an id — it rewrites `placed[].itemId` in every layout *and* inside the `furnHist` snapshots, so an undo can't bring the old id back. `uniqueId(base, taken)` is the `-2`/`-3` collision suffix used by Duplicate and by import.
- **Export / import**: both go through a modal that picks what moves. `exportPayload()` writes a partial state — `{app, version, exported, folders, layouts, inventory}` plus the `PREF_KEYS` if settings were ticked — where any part may be empty; picking a room silently locks on the things standing in it so placements survive the trip. `readImport()` reads such a file back without assuming it is a whole project (a things-only file is valid), and `applyImport()` either replaces the project or merges: an item id that already exists here either wins ("keep mine", the rooms coming in re-point at yours) or is added beside it as `id-2`, a folder id that already exists **is** that folder, and placements whose thing resolves to nothing are dropped. `normLayout()`/`normItem()` are split out of `migrate()` so one room or one thing lifted out of a file gets the same clean-up — put new per-room/per-item shape fixes there, not in `migrate()` directly.
- **Blueprint import** (`bp*`, **[src/features/blueprint/](src/features/blueprint/)**, 22 modules): traces a photo of a floor plan into rooms on a floor. Four stages in one `#modal` — choose a photo, crop, find the rooms, review — chained by the fact that an `onOk` returning `false` leaves the modal open, so each stage just replaces the body. `openModal` gained `opts.wide` and `opts.onClose` for this; `onClose` fires however the modal goes away (OK, Cancel, backdrop, Esc) and is where `bpDispose()` revokes the object URL. **The photo never touches `S`** — `save()` serialises the whole of `S` into localStorage, so megabytes of base64 there would break saving permanently and silently; it lives in the module-level `bpState` (**[src/features/blueprint/state.js](src/features/blueprint/state.js)**, a leaf that imports nothing) until commit, then it is dropped. `bpState` is written from the wizard's step dialogs, which are other modules now, so those writes go through `setBpState(v)` — the same rule as `setS`. Detection is a *proposal*: `bpState.proposal` is never mutated, corrections land in `bpState.edits`, and `bpRebuild()` derives the draft from scratch each time (changing the scale moves every room, so that has to stay idempotent over edits already made). `bpCleanPoly()` (**[src/features/blueprint/poly.js](src/features/blueprint/poly.js)**) normalises winding, drops collinear vertices and merges sub-50mm edges **before** `polySimple()` — which is the only polygon gate; a weakened copy of it is what made an earlier attempt's rooms permanently uneditable. The import is not on any undo stack (the three stacks can't express creating a floor plus N rooms), so `bpLastImport` powers an explicit "Undo this import" instead (**[src/features/blueprint/commit.js](src/features/blueprint/commit.js)**, reached from `floorMenu`). **Dividers** (`bpStampSplit`/`bpDeriveRegions`/`bpMarkSeams`) split one open region into two named rooms with no wall between them: a divider is a seed point plus an axis, stamped as a single pixel of barrier into a *copy* of the mask, after which the regions are re-derived by the same code the first pass ran — so merging two rooms is deleting a divider, and there is no polygon union anywhere in the region. The four wizard stages are one module each (`step1-upload.js` .. `step4-review.js`), and none imports another: each `bpXStage(..., to)` leaves only through `to.next()`/`to.back()`, the moves **[flow.js](src/features/blueprint/flow.js)** hands it, so the order is written once there and `bpUploadDialog` (the entry point) is flow.js's. Where a divider is proposed comes from `bpLabelBlocks()`, which finds the *positions* of name labels (S5 is what reads them) out of the small components the largest-component step discards. The resulting seam is cut out of the room's edge as an edge of its own and carries `wallOff`, which is what makes `floorSnapCandidates` report "Open through" and `floorEdgeDepths` draw nothing there.
- **Validation**: `validate(inst, poly)` / `insideRoom()` / `collides()` are the single source of truth for whether a piece of furniture placement is legal; reuse them rather than re-deriving overlap/bounds logic.
- **Measuring**: the canvas's Measure toggle (`#btnMeasure`, key `M`) sets `measureOn`, and while it's on the Measure tool (`features/measure/measure-tool.js`) is the active tool, so a click picks anchors instead of editing, in either mode. Measurements live on the layout as `l.measures = [{id, a, b}]`. Each end is an anchor `{k, id, part, n}`: `k` is `item|pillar|iwall|open|wall` (`id` is a room wall's *index*), and `part` is `corner`, `side` (with `n`), `whole`, or `swing` (a hinged door's `swingPoly()`, only pickable while door swings are shown). `measureObjs()` lists what can be measured and the anchors each offers. `anchorGeom()` turns an anchor into a point, segment or solid polygon, and `closestBetween()` gives the shortest distance between two of them. Ends are looked up on every draw, so a measurement follows what it joins; one whose end is missing is skipped rather than deleted (undo can bring it back), and `pruneMeasures()` drops it on load. Anything that gives things new ids (duplicating a room, importing one) must go through `remapMeasures()`. Measurements have no undo history.
- **Open state**: an inventory item may carry `item.open = {top,bottom,left,right}` (mm out past its own footprint, in the item's unrotated frame). `openPoly(inst,item)` is that footprint in world space and `openConflicts()` reports, per placed id, what it runs into. This is deliberately kept **out** of `validate()` — an open footprint never makes a placement illegal, it only warns — so don't fold it into the validity path.

## Conventions
- No semicolon-free style; ES2017-ish, `"use strict"`. JS with JSDoc types, checked by `tsc` (`npm run typecheck`); no `.ts` source files — the only TypeScript is declaration files (`*.d.ts`) for shared types. Annotate what a strict module exports; prefer a precise type to a cast, and a cast to `any`; every cast or `any` that asserts something tsc cannot see says why in a comment. Keep new code consistent with the surrounding style.
- **Components** are `.jsx` modules (Preact, automatic JSX runtime), strict from their first line, written as `function` components with HTML's own attribute names (`class`, `for`). A component holds its own elements: no `innerHTML`, no `$('id')` lookups, no listeners on `document`, nothing read from the DOM at import time; lists are keyed by the model's ids; state the model does not hold (a drag in flight, which row is being renamed) is a hook or a signal in the feature. An `id` stays only where something needs it (a `<label for>`).
- New code goes in the `src/` module, partial or stylesheet where it belongs — **not** in `index.html`, which is a shell. The one thing that still belongs there is a listener registration, at the spot its markup implies. (The split that got here is written up in [`.claude/plans/refactor-split.md`](.claude/plans/refactor-split.md); the mechanical recipe in §4 is worth reading before any large move.)
- **Runtime dependencies are small, bundle into the single file, and have a stated reason.** The current list and its reasons are under *What this is*; anything more is a decision, not a convenience.
- Contributor-facing setup and review expectations are in [`CONTRIBUTING.md`](CONTRIBUTING.md); it is the same ground as this file, written for a person arriving cold.
- `function` declarations stay `function` declarations — never rewritten as `const f = () => {}`. ESM tolerates import cycles for hoisted function declarations but not for `const` bindings read during module evaluation, and this graph is dense and almost certainly cyclic.
- Angles: 0° points right, 90° points up (screen-plan convention), see `wallAngle`/`setWallAngle`.
