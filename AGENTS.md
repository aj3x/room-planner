# AGENTS.md

## What this is
Room Planner is a client-only web app with **zero runtime dependencies**. What ships is one self-contained HTML file you can open off disk — that deployment model is not negotiable — but it is *built* rather than hand-maintained:

```sh
npm install && npx playwright install chromium   # once
npm run dev        # Vite dev server on http://127.0.0.1:5173, HMR on save
npm run build      # -> dist/index.html, one file, everything inlined
npm test           # 109 Vitest + 26 Playwright, ~45s
npm run lint       # ESLint, correctness rules only
```

`dist/` is **never committed** — a generated 322 kB file touched by every PR conflicts on every merge, which is the exact problem the module split exists to solve. It is gitignored, and CI fails if it is ever tracked. Both workflows live in [`.github/workflows/`](.github/workflows): `ci.yml` runs lint, unit, build and the browser suite on every pull request; `pages.yml` builds and publishes `dist/` to GitHub Pages on every push to `main`. Review routing is in [`.github/CODEOWNERS`](.github/CODEOWNERS).

Two consequences worth knowing before you touch anything:

- **`index.html`'s one `<script>` is `type="module"`** (a Vite entry point), so the source file does **not** run from `file://` — module scripts are fetched under CORS rules an opaque `file://` origin cannot satisfy. Open `dist/index.html` for that, which is what actually ships.
- **All tooling is a devDependency.** `dependencies` in `package.json` is empty and must stay that way.

### Moving code between modules

The split is done, but code still moves, and the two findings that cost the most to learn are worth having before you start.

**When a big function looks unmovable, check whether what is really stuck is the mutable state it reads, not the code.** `draw()` was called an unbisectable 1,500-line component; it moved as an ordinary 766-line commit once the state it reads had moved out ahead of it. **Mutable shared state belongs in leaf modules that import nothing** — `core/state.js` (`S`), `core/selection.js` (the ten selection lets), `canvas/interaction-state.js`, `canvas/measure-state.js`, `library/nav.js`. Keep it that way.

**That does not dissolve every knot, so check which kind you have.** The Plan side panels and the Library UI were once one strongly-connected component of 49 names, and its six edges were plain function calls rather than shared state — no setter breaks that, and it had to move whole, in one commit of 1,326 lines into 15 modules. Ask the question explicitly (state, or calls?) rather than assuming the `draw()` answer.

**A move is a move.** Byte-identical lines, no renames, no reordering, no reformatting, no fixes folded in; `git blame` survives a pure move and that history is what settles an argument later. A behaviour change — a `setX(v)` setter, say — goes in its own commit and says so in the message. Bugs you spot go in `BACKLOG.md`.

**Four more rules carry forward, and all four have drawn blood.**

1. **No import edge that drags an existing top-level read into a cycle.** `canvas/view.js` runs `const cv=$('cv'), ctx=cv.getContext('2d')` at module-eval time, and `$` comes from `ui/modal.js`. The module graph has exactly two cycles: `modal.js ↔ panels.js ↔ tag-input.js`, and a 45-module one holding nearly everything else. **`ui/modal.js` must stay outside the big one** — that is the whole reason `migrate()` is in `core/migrate.js` and not `core/store.js` (which `ui/panels.js` imports), `setMode` and `togglePane` are in `plan/mode.js` and not `ui/panels.js`, and `savePlanImage` is in `io/export.js` and not `canvas/`. Nothing in `ui/` may import `plan/` or `library/`. Check any new edge with a Tarjan run over the import graph, not by eye.
2. **`test/epilogue.js` is not linted.** `__rp` names a binding that must still be in `index.html`'s scope; when the last reader moves out, you get a bare `ReferenceError` at module evaluation, with a green build and a green browser. Where a name has moved, the epilogue **imports** it rather than `index.html` importing it back. Worse are the `GLOBALS` entries, which assign inside a `try/catch` and so fail *silently* and late. There is a standing audit for both; see `test/README.md`.
3. **Listener registrations stay in `index.html`**, at their exact spot. A module that calls `addEventListener` at import time introduces a top-level side effect *and* reorders that listener ahead of every other one in the file. The pointer handlers drive `canvas/interaction.js` through `applyDragAt`/`cancelDrag`/`endDrag`; the pane heads drive `togglePane`; and so on. A binding a staying listener writes needs a `setX(v)` setter, because you cannot assign to an imported binding.
4. **ESLint cannot check a module specifier.** `import {sizeLabel} from '../model/measures.js'` lints clean even though `sizeLabel` is exported by `canvas/draw.js` — `no-undef` sees the name as declared by the import either way, and there is no import resolver in `eslint.config.js`. A real name behind the wrong file is invisible to lint and is found only by running the suite. Verify the *module*, not just the name.

**There are no top-level side effects anywhere in `src/`.** Every module defines and exports; nothing runs at import time. **`src/boot.js` exports `boot()` and `index.html` calls it**, at the exact line its IIFE occupied. That is deliberate and worth not undoing — importing a `boot.js` that called `boot()` itself would run boot *before* `index.html`'s listener registrations, since imports hoist and evaluate ahead of the importing module's body. It would happen to work, because `boot()` suspends on its first `await`, but nothing in the suite would catch it if that stopped being true. The `edgePanTick` rAF loop is the same shape, exported from `canvas/interaction.js`.

**Styles are SCSS, and `src/styles/main.scss` is where the cascade order is stated.** The partials are plain CSS cut on the banners that were already in the `<style>` block, so `@use` order *is* source order and later rules still win ties on equal specificity — put a rule where it belongs in the sequence, not at the end. Nothing is nested and nothing uses `@extend`; if you nest, the cap is two levels plus `&` modifiers. **The design tokens are CSS custom properties and must stay that way** — dark mode re-declares all 24 under `@media (prefers-color-scheme:dark)`, and a Sass `$variable` is compile-time and cannot cascade, so converting one deletes dark mode with every test still green. See [DESIGN.md](DESIGN.md) §3.2.

**The static markup lives in `src/html/`, behind `<!-- @include src/html/foo.html -->`.** A local Vite plugin, `rp:html-includes` in [vite.config.js](vite.config.js), substitutes each directive in `transformIndexHtml`. It runs first in the chain (`enforce: 'pre'`, `order: 'pre'`), so the epilogue, `rp:classic-script-tag` and `vite-plugin-singlefile` all see one whole document. **It is a textual splice and must stay one** — the panes are static markup the browser parses before any script runs, which is exactly what every `render*()` function assumes when it looks up `#paneRoom` or `#libContent` at boot; rebuilding them from JS template strings would be a behaviour change. `test/unit-setup.js` carries the same four-line substitution, because it reads `index.html` off disk instead of through Vite — **keep the two in step**, or the jsdom shell has no `#cv` and the app dies at module evaluation with a wall of red unit tests, a green build and a green browser.

The header nav (`#navSeg`) switches between three **places**: **Plan** (the canvas + side panels), **Library** and **Marketplace** (a full-width library UI, `#paneLibrary`, that swaps in for `<main>` when active — see `isCanvasMode()`/`applyLayoutMode()`). Inside Plan, the **Room | Furniture** mode switch (`#modeSeg`) sits on the canvas itself. `S.mode` is one of `'room'|'furniture'|'inventory'|'marketplace'`; `S.planMode` remembers which canvas mode to return to from the header. `setMode()` (**[src/plan/mode.js](src/plan/mode.js)**) toggles between the canvas layout and the library layout and, for the latter, calls `renderLibAll()` instead of `draw()`.

**Design rules live in [DESIGN.md](DESIGN.md)** — tokens, components, wording ("item", "Library", never "thing"/"inventory" in UI copy) and a review checklist. Read it before adding UI; all colours, sizes, radii and shadows come from the CSS custom properties in [`src/styles/_tokens.scss`](src/styles/_tokens.scss), never literals.

To preview: `npm run dev`, or `npm run build && open dist/index.html` to check the shipped artifact.

## Verifying changes
`npm test` is the gate, and CI (`.github/workflows/ci.yml`) runs the same commands on every pull request, plus a check that nothing under `dist/` is tracked. Read [`test/README.md`](test/README.md) before touching anything under `test/` — it opens with the rule that shapes the directory: **test code stays under 20% of the codebase, and ideally under 10%** (it is 1,435 lines against 12,948 today). The characterization baseline that guarded the module split has been removed now that the split has landed; what is left is a permanent suite, and every addition to it needs an argument about what it catches that nothing else does.

- `npm run test:unit` (~2s) — Vitest + jsdom: units, `migrate()` goldens and import/export round-trips, imported straight out of `src/`, plus the build-pipeline tests.
- `npm run test:e2e` (~40s) — builds, then Playwright + Chromium against **both** the dev server and `dist/index.html`, sharing one set of goldens so the build cannot move a coordinate unnoticed. Covers the smoke path, the blueprint geometry golden, two pointer gestures and the `file://` deployment contract.
- **What it does NOT cover** is written down in `test/README.md` — the side panels, the canvas's pixels, most pointer interaction and the marketplace. A break in any of those turns nothing red, so exercise them by hand.
- `npm run lint` — ESLint, correctness rules only. No Prettier and no formatting rules, deliberately: the dense style here is a decision, and reformatting 10k lines would destroy `git blame`. `no-undef` is the rule that earns its keep.

Still worth doing by hand for anything visual: `npm run dev` and exercise the area you changed (draw/resize a room, place furniture, undo/redo, switch units).

## Architecture
- **Units** (**[src/core/units.js](src/core/units.js)**, imported at the top of `<script>`): everything is stored internally in **millimetres**; `parseLen`/`fmtLen` convert to/from the user's display unit (ft+in, in, cm, mm, m). Don't introduce a second unit system — always store mm and format at render time. Geometry helpers are in **[src/core/geometry.js](src/core/geometry.js)**.
- **State** (**[src/core/state.js](src/core/state.js)**): a single global `S` object holds `layouts` (rooms), `inventory` (furniture items), `folders`, and UI prefs (unit, snap, mode). Each layout's room is a closed polygon: `room.points = [[x,y], ...]` (clockwise, mm).
- **Persistence**: `Store` wraps `window.storage` (if present) or falls back to `localStorage`. `save()` debounces writes. `migrate(st)` (**[src/core/migrate.js](src/core/migrate.js)**, *not* `store.js` — see the cycle rule above) upgrades older saved-state shapes on load — **when changing the shape of `S`, add a migration step here** rather than assuming fresh state. `S` itself is reassigned wholesale on load and on import; it lives in a module now and you cannot assign to an imported binding, so every such write goes through `setS(v)` (**[src/core/state.js](src/core/state.js)**), never a bare `S = …`.
- **Inventory tab**: organizes the same `S.inventory` used by Furniture mode, adding `item.folderId`/`item.manualTags` alongside the existing `item.tags` (the folder-inherited half — see `applyTags`/`reconcileTags`), plus top-level `S.itemFolders` (a folder tree with `tags:[]` materialized onto everything filed under it). Browsing is a folder tree (`#tree`) + grid (`#libContent`); editing an item's shape/color/count/etc. reuses the *same* `itemDialog(id)` modal (**[src/plan/item-dialog.js](src/plan/item-dialog.js)**) as Furniture mode's "Add a thing" — the Inventory tab doesn't have its own item editor. Its own Export (`exportLibraryDialog`/`exportLibFolder`/`exportLibItems`) writes `{app, version, exported, inventory}`, the same shape `ITEM_SCHEMA.md` documents, so it round-trips through the app's main Import.
- **Marketplace tab**: two independent sources, both landing on the same `addMarketItemToInventory()` collision flow (see **Marketplaces** below):
  - **Subscriptions** (`S.marketSubs`): live `market.json` URLs per **[MARKET_SCHEMA.md](MARKET_SCHEMA.md)**. `subscribeMarket()`/`reloadMarketSub()`/`removeMarketSub()`/`fetchMarketItem()` fetch and validate `app`/`version` on every manifest, index shard, and item file. `marketIndexCache`/`marketItemCache` are in-memory `Map`s, never persisted — only the subscription record itself (`{id,url,name,version,itemURL}`) is saved.
  - Clicking a subscribed item opens `renderMarketItemPreview()` as a dialog (its "Add to library" defers `addMarketItemToInventory()` with `setTimeout`, so a collision dialog can open after the preview closes).
  - **Ad hoc listings** (`S.marketListings`/`S.marketFolders`): the older upload/paste-JSON/flat-link path, for sharing a one-off bundle without hosting a repo. Unrelated to the schema above.
- **Undo/redo**: room edits and furniture edits have **separate** history stacks (`roomHist`/`furnHist`), keyed per-layout. Use `commitRoom()`/`commitFurn()` after any change that should be undoable — don't mutate state without a corresponding commit.
- **Rendering** (the camera is **[src/canvas/view.js](src/canvas/view.js)**: `cv`, `ctx`, `view`, `sx`/`sy`/`wx`/`wy`, `snapPt`): `draw()` redraws everything to `<canvas id="cv">` every time state changes (immediate-mode, no diffing/virtual DOM). Side-panel HTML is rebuilt via `render*()` functions (`renderRoom`/`renderWalls` in **[src/plan/room-panel.js](src/plan/room-panel.js)**, `renderInv` in **[src/plan/item-list.js](src/plan/item-list.js)**, `renderSel` in **[src/plan/selection-panel.js](src/plan/selection-panel.js)**, `renderAll` in **[src/plan/mode.js](src/plan/mode.js)**) that re-set `innerHTML` and re-bind listeners — follow this same pattern for new UI rather than introducing a framework.
- **Side panels**: left `#paneRoom` ("Plan") holds *lists* — rooms, then the items (Furniture mode) or walls/doors/structure (Room mode); right `#paneStuff` ("Properties") holds the *selection* first, then room properties / stock, then View settings. Sections meant for one mode carry `for-room` or `for-furn` and are hidden by `body[data-mode]` (set in `renderMode()`). Each `.pane` is a `.pane-head` rail plus a `.pane-body`; `applyPanes()` drives `S.leftOpen`/`S.rightOpen` and the `lc`/`rc` classes on `<main>`. Collapsing is desktop-only: under 900px the panes become `display:contents`, the canvas is sticky on top, and sections stack in the order set by `section[data-sec=…]{order}` in the narrow media query. Every `section` has a `.sec-head` (an `h2` that toggles collapse, plus optional `.sec-act` buttons such as the `+` that adds to that list) and a `data-sec` key persisted in `S.secClosed` — new sections need both.
- **Icons, dialogs, toasts** (**[src/ui/modal.js](src/ui/modal.js)**, **[src/ui/flash.js](src/ui/flash.js)**): icons are `<symbol>`s in the sprite at the top of `<body>`; render them with `svgI('name')` (no emoji). `openModal(title, html, okLabel, onOk, onMount, {danger:true})` styles a destructive action; `askConfirm()` always does. `flash()`/`libFlash()` stay up for `readTime(msg)`. `$(id)` and `esc(s)` — the two helpers every render path uses — are exported from `src/ui/modal.js` and `src/ui/panels.js` respectively.
- **Canvas colours** (**[src/canvas/draw.js](src/canvas/draw.js)**): `draw*()` functions read colours from `PAL()` (`CANVAS.light`/`CANVAS.dark`, following `prefers-color-scheme`), never literals. Only stage-side colours (background, walls, labels) differ in dark mode; selection/handles/warnings sit on the user's floor colour and keep light values. `savePlanImage()` (reached from the Export dialog) forces the light palette.
- **Double-click**: a wall opens `wallDialog(i)` — from the plan (canvas `dblclick` → `pickRoom`, Room mode only) or from a row in the Walls list. It is the same length/direction pair as the Selected panel, and it leans on `setWallLen`/`setWallAngle` returning false when `tryRoomEdit` rolls the change back, in which case the modal stays open over the flash message.
- **Row menus** (**[src/ui/menu.js](src/ui/menu.js)**, **[src/ui/inline-edit.js](src/ui/inline-edit.js)**): the `⋯` buttons (`moreBtn()`) open an anchored `openMenu(anchor, actions, title)` popup, not the modal. Actions that need more than one click (rename with a box, pick a folder, confirm a delete) open the modal *from* the menu. Renaming in place is `inlineEdit(el, value, done)`; because a row re-renders on a single click, click handlers on those rows go through `singleClick()`/`cancelSingleClick()` so a second click can become a double-click instead.
- **Reordering** (**[src/ui/dnd.js](src/ui/dnd.js)**): the layout tree and the inventory list use HTML5 drag-and-drop. `moveBefore(arr, movedId, targetId, after)` does the splice — folders and rooms live in separate arrays (`S.folders`, `S.layouts`), so a drop only reorders against its own kind and otherwise just reparents. `folderDescendant()` is the cycle guard.
- **Inventory scope**: `S.invScope` (`project` | `folder` | `room`, see `INV_SCOPES`) decides which rooms `usedCount()` counts, via `scopeLayouts()`. `folder` means the rooms sitting *directly* in the active room's folder — a subfolder is its own pool and never draws on the folder above it.
- **Modal dialogs** (**[src/ui/modal.js](src/ui/modal.js)**): implemented as a plain `<div>` (`#modal`), never `<dialog>` or `<form>` — the code comment explains both are blocked in sandboxed iframes this app may run in. Keep using `openModal()`/`closeModal()`.
- **Ids**: an inventory item's id is user-editable (Advanced, inside the edit dialog), so it is held to a URL/S3-safe character set by `idProblem()` — letters, digits, `! - _ . * ' ( )`, and `/` between path parts (no leading, trailing, or doubled slash). A slash reads like an S3 key: `ikea/kallax/4x2` and `ikea/kallax/2x4` sit in the same folder — both the Inventory tab's own folder tree (`rehomeItemId()` keeps an item's id filed under its folder path) and a subscribed marketplace's browse view (`marketPathChildren()` derives folders straight from id path segments, no separate folder list) use this convention. `retagItem()` is the only sanctioned way to change an id — it rewrites `placed[].itemId` in every layout *and* inside the `furnHist` snapshots, so an undo can't bring the old id back. `uniqueId(base, taken)` is the `-2`/`-3` collision suffix used by Duplicate and by import.
- **Export / import**: both go through a modal that picks what moves. `exportPayload()` writes a partial state — `{app, version, exported, folders, layouts, inventory}` plus the `PREF_KEYS` if settings were ticked — where any part may be empty; picking a room silently locks on the things standing in it so placements survive the trip. `readImport()` reads such a file back without assuming it is a whole project (a things-only file is valid), and `applyImport()` either replaces the project or merges: an item id that already exists here either wins ("keep mine", the rooms coming in re-point at yours) or is added beside it as `id-2`, a folder id that already exists **is** that folder, and placements whose thing resolves to nothing are dropped. `normLayout()`/`normItem()` are split out of `migrate()` so one room or one thing lifted out of a file gets the same clean-up — put new per-room/per-item shape fixes there, not in `migrate()` directly.
- **Blueprint import** (`bp*`, **[src/blueprint/](src/blueprint/)**, 20 modules): traces a photo of a floor plan into rooms on a floor. Four stages in one `#modal` — choose a photo, crop, find the rooms, review — chained by the fact that an `onOk` returning `false` leaves the modal open, so each stage just replaces the body. `openModal` gained `opts.wide` and `opts.onClose` for this; `onClose` fires however the modal goes away (OK, Cancel, backdrop, Esc) and is where `bpDispose()` revokes the object URL. **The photo never touches `S`** — `save()` serialises the whole of `S` into localStorage, so megabytes of base64 there would break saving permanently and silently; it lives in the module-level `bpState` (**[src/blueprint/state.js](src/blueprint/state.js)**, a leaf that imports nothing) until commit, then it is dropped. `bpState` is written from the wizard's step dialogs, which are other modules now, so those writes go through `setBpState(v)` — the same rule as `setS`. Detection is a *proposal*: `bpState.proposal` is never mutated, corrections land in `bpState.edits`, and `bpRebuild()` derives the draft from scratch each time (changing the scale moves every room, so that has to stay idempotent over edits already made). `bpCleanPoly()` (**[src/blueprint/poly.js](src/blueprint/poly.js)**) normalises winding, drops collinear vertices and merges sub-50mm edges **before** `polySimple()` — which is the only polygon gate; a weakened copy of it is what made an earlier attempt's rooms permanently uneditable. The import is not on any undo stack (the three stacks can't express creating a floor plus N rooms), so `bpLastImport` powers an explicit "Undo this import" instead (**[src/blueprint/commit.js](src/blueprint/commit.js)**, reached from `floorMenu`). **Dividers** (`bpStampSplit`/`bpDeriveRegions`/`bpMarkSeams`) split one open region into two named rooms with no wall between them: a divider is a seed point plus an axis, stamped as a single pixel of barrier into a *copy* of the mask, after which the regions are re-derived by the same code the first pass ran — so merging two rooms is deleting a divider, and there is no polygon union anywhere in the region. The four wizard stages are one module each (`step1-upload.js` .. `step4-review.js`) and they are a **cycle**: each stage's `onOk` calls the next and its Back handler calls the one before. Every edge is a function declaration called from inside a function body, and the only top-level binding among the four is `step3-scale.js`'s `BP_STEPS` array literal, so nothing is read at module-evaluation time — do not add a top-level read across that cycle. Where a divider is proposed comes from `bpLabelBlocks()`, which finds the *positions* of name labels (S5 is what reads them) out of the small components the largest-component step discards. The resulting seam is cut out of the room's edge as an edge of its own and carries `wallOff`, which is what makes `floorSnapCandidates` report "Open through" and `floorEdgeDepths` draw nothing there.
- **Validation**: `validate(inst, poly)` / `insideRoom()` / `collides()` are the single source of truth for whether a piece of furniture placement is legal; reuse them rather than re-deriving overlap/bounds logic.
- **Measuring**: the canvas's Measure toggle (`#btnMeasure`, key `M`) sets `measureOn`, and while it's on `pointerdown` goes to `measurePointerDown()` instead of editing, in either mode. Measurements live on the layout as `l.measures = [{id, a, b}]`. Each end is an anchor `{k, id, part, n}`: `k` is `item|pillar|iwall|open|wall` (`id` is a room wall's *index*), and `part` is `corner`, `side` (with `n`), `whole`, or `swing` (a hinged door's `swingPoly()`, only pickable while door swings are shown). `measureObjs()` lists what can be measured and the anchors each offers. `anchorGeom()` turns an anchor into a point, segment or solid polygon, and `closestBetween()` gives the shortest distance between two of them. Ends are looked up on every draw, so a measurement follows what it joins; one whose end is missing is skipped rather than deleted (undo can bring it back), and `pruneMeasures()` drops it on load. Anything that gives things new ids (duplicating a room, importing one) must go through `remapMeasures()`. Measurements have no undo history.
- **Open state**: an inventory item may carry `item.open = {top,bottom,left,right}` (mm out past its own footprint, in the item's unrotated frame). `openPoly(inst,item)` is that footprint in world space and `openConflicts()` reports, per placed id, what it runs into. This is deliberately kept **out** of `validate()` — an open footprint never makes a placement illegal, it only warns — so don't fold it into the validity path.

## Conventions
- No semicolon-free style; ES2017-ish, `"use strict"`, no TypeScript. Keep new code consistent with the surrounding style.
- New code goes in the `src/` module, partial or stylesheet where it belongs — **not** in `index.html`, which is a shell. The one thing that still belongs there is a listener registration, at the spot its markup implies. (The split that got here is written up in [`.claude/plans/refactor-split.md`](.claude/plans/refactor-split.md); the mechanical recipe in §4 is worth reading before any large move.)
- **No runtime dependencies.** `dependencies` in `package.json` is empty and stays empty.
- Contributor-facing setup and review expectations are in [`CONTRIBUTING.md`](CONTRIBUTING.md); it is the same ground as this file, written for a person arriving cold.
- `function` declarations stay `function` declarations — never rewritten as `const f = () => {}`. ESM tolerates import cycles for hoisted function declarations but not for `const` bindings read during module evaluation, and this graph is dense and almost certainly cyclic.
- Angles: 0° points right, 90° points up (screen-plan convention), see `wallAngle`/`setWallAngle`.
