# AGENTS.md

## What this is
Room Planner is a client-only web app with **zero runtime dependencies**. What ships is still one self-contained HTML file you can open off disk — that deployment model is not negotiable — but as of the `refactor/modularize` branch it is *built* rather than hand-maintained:

```sh
npm install && npx playwright install chromium   # once
npm run dev        # Vite dev server on http://127.0.0.1:5173, HMR on save
npm run build      # -> dist/index.html, one file, everything inlined
npm test           # 185 Vitest + 436 Playwright, ~75s
npm run lint       # ESLint, correctness rules only
```

`dist/` is **never committed** — a generated 547 KB file touched by every PR conflicts on every merge, which is the exact problem this refactor exists to solve.

Two consequences worth knowing before you touch anything:

- **`index.html`'s one `<script>` is now `type="module"`** (a Vite entry point). The code inside it is unchanged, but the source file no longer runs from `file://` — module scripts are fetched under CORS rules an opaque `file://` origin cannot satisfy. Open `dist/index.html` for that, which is what actually ships.
- **All tooling is a devDependency.** `dependencies` in `package.json` is empty and must stay that way.

Almost everything still lives in the single file **[index.html](index.html)** — all its HTML, CSS and most of its JS, one `<style>` and one `<script>`. Phase 3 is splitting the JS into `src/`, one region at a time. Moved so far: **`src/core/`** — `units.js`, `geometry.js`, `open-state.js`, `state.js`, `selection.js`, `ids.js`, `floor-space.js`, `store.js`, `history.js`; **`src/model/`** — `walls.js`, `openings.js`, `validity.js`, `measures.js`, `walkpaths.js`; **`src/ui/`** — `modal.js`, `menu.js`, `inline-edit.js`, `dnd.js`, `tag-input.js`, `panels.js`, `flash.js`; **`src/canvas/`** — `view.js`, `draw.js`, `snap.js`, `merge-rooms.js`, `split-room.js`, `interaction-state.js`, `measure-state.js`, `measure-tool.js`; and **`src/plan/`** — `layout-tree.js`, `room-panel.js`, `item-list.js`. `src/model/walls.js`, `src/model/walkpaths.js`, `src/ui/flash.js` and `src/canvas/view.js` are **whole**.

**`draw()` has moved.** It is in **[src/canvas/draw.js](src/canvas/draw.js)** with the whole `drawing` banner — the floor plan, the arranging magnet, the grid, walls, openings, items, handles and the status readout — along with the four `draw*()` helpers that used to block it. The `canvas/` round called it one unbisectable ~1,500-line component; it turned out not to be, once the state it reads moved out ahead of it. **That is the lesson worth carrying:** when a big function looks unmovable, check whether what is really stuck is the *mutable state* it reads, not the code. Mutable shared state belongs in leaf modules that import nothing — `core/state.js` (`S`), `core/selection.js` (the nine selection lets), `canvas/interaction-state.js` (`drag` and the draw-mode lets), `canvas/measure-state.js` — and a binding that is reassigned from outside its module needs a `setX(v)` setter, because you cannot assign to an imported binding.

**The next gate is not one function, it is a cycle — and this is the thing to know before planning another round.** The Plan side panels and the Library UI call each other: `setMode()` and `itemDialog()` call `renderLibAll()`, and `createLibItem`/`libItemMenu`/`bindLibGrid`/`deleteLibItem` call back into `itemDialog()`/`renderSel()`. Six edges, all plain function calls — no shared mutable state, so the `draw()` trick above does **not** apply here; it was checked. A Tarjan run over the reference graph puts the damage at **one strongly-connected component of 48 names and 1,224 lines**, holding `renderRoom`, `renderRoomSel`, `renderSel`, `renderWallProps`, `renderOpeningProps`, `splitWall`, `deleteCorner`, `setMode`, `itemDialog` and `openingDialog` on the Plan side and most of the library on the other.

An SCC cannot be split across commits — any part of it left in `index.html` is unreachable from `src/`, which cannot import from `index.html`. So it lands in **one** commit, after the rest of `library/` + `io/` has moved. `plan/` cannot be a round before `library/`; they are the same round. And that commit sits on the least-tested code in the repo, so read `test/README.md` on side-panel coverage before starting.

Still in the monolith and blocked **on that SCC**: `canvas/room-draw.js`, `canvas/corners.js`, `canvas/interaction.js`, the rest of `canvas/split-room.js`, `squareCorner` in `snap.js`, `setMeasure`, the UI half of `merge-rooms.js`, the replaying half of `core/history.js` (`applyRoomSnap`/`applyFurnSnap`/`applyFloorSnap` and the six undo/redo entry points) and most of `plan/`.

`togglePane` is blocked on something else, and it is a trap worth naming. It needs `resize()`, which has moved — but putting `togglePane` in `ui/panels.js` adds a `panels.js → canvas/view.js` edge, and `ui/modal.js` and `ui/panels.js` already import each other. That drags `view.js` into their cycle, where its top-level `const cv=$('cv'), ctx=cv.getContext('2d')` runs before `modal.js` has initialised `$` — **`TypeError: $ is not a function`, app dead at boot**. Tried, 69 unit tests red, reverted. The rule is not just "no top-level read across a cycle"; it is **"no import edge that drags an existing top-level read into one"**.

Two conventions the `ui/` round set, worth keeping to. **Listener registrations stay in `index.html`** — a module that calls `addEventListener` at import time both breaks the "only `boot.js` has top-level side effects" rule and moves that listener ahead of every other one in the file, which is a behaviour change. The registrations that trail the modal, menu and pane regions sit where they always did and read `mo`/`menuEl`/`applyPanes` as imported bindings. The `canvas/` round kept to it: `const cv=$('cv'), ctx=cv.getContext('2d')` moved into `src/canvas/view.js` (it is a lookup plus a memoising lazy accessor, not a mutation), but the `darkMQ` `change` listener beside it stayed in `index.html`. And **`src/ui/modal.js` and `src/ui/tag-input.js` import each other** on purpose: `openModal()` clears `tagInputs`, `mountTagField()` calls `$()`. Both uses are inside function bodies, so nothing is read at module-evaluation time and the cycle is safe — but do not add a *top-level* read across that edge. Treat the monolith as the source of truth for everything that is still in it, and see [`.claude/plans/refactor-split.md`](.claude/plans/refactor-split.md) § "How to extract a region" before moving anything else. The header nav (`#navSeg`) switches between three **places**: **Plan** (the canvas + side panels), **Library** and **Marketplace** (a full-width library UI, `#paneLibrary`, that swaps in for `<main>` when active — see `isCanvasMode()`/`applyLayoutMode()`). Inside Plan, the **Room | Furniture** mode switch (`#modeSeg`) sits on the canvas itself. `S.mode` is one of `'room'|'furniture'|'inventory'|'marketplace'`; `S.planMode` remembers which canvas mode to return to from the header. `setMode()` toggles between the canvas layout and the library layout and, for the latter, calls `renderLibAll()` instead of `draw()`.

**Design rules live in [DESIGN.md](DESIGN.md)** — tokens, components, wording ("item", "Library", never "thing"/"inventory" in UI copy) and a review checklist. Read it before adding UI; all colours, sizes, radii and shadows come from the CSS custom properties at the top of `<style>`, never literals.

To preview: `npm run dev`, or `npm run build && open dist/index.html` to check the shipped artifact.

## Verifying changes
`npm test` is the gate. It is a **characterization baseline** — a recording of how the app behaved before the module split, whose job is to prove the split changed nothing — so read [`test/README.md`](test/README.md) before touching anything under `test/`. The short version: **a red test during this refactor means the refactor is wrong, not that the test is stale.**

- `npm run test:unit` (~3s) — Vitest + jsdom: the data model, migrations, units, import/export round-trips, plus the build-pipeline tests.
- `npm run test:e2e` (~20s) — builds, then Playwright + Chromium against **both** the dev server and `dist/index.html`, sharing one set of screenshot baselines so the build cannot move a pixel unnoticed.
- `npm run lint` — ESLint, correctness rules only. No Prettier and no formatting rules, deliberately: the dense style here is a decision, and reformatting 10k lines would destroy `git blame`. `no-undef` is the rule that earns its keep.

Still worth doing by hand for anything visual: `npm run dev` and exercise the area you changed (draw/resize a room, place furniture, undo/redo, switch units).

## Architecture (all inside index.html)
- **Units** (**[src/core/units.js](src/core/units.js)**, imported at the top of `<script>`): everything is stored internally in **millimetres**; `parseLen`/`fmtLen` convert to/from the user's display unit (ft+in, in, cm, mm, m). Don't introduce a second unit system — always store mm and format at render time. Geometry helpers are in **[src/core/geometry.js](src/core/geometry.js)**.
- **State** (**[src/core/state.js](src/core/state.js)**): a single global `S` object holds `layouts` (rooms), `inventory` (furniture items), `folders`, and UI prefs (unit, snap, mode). Each layout's room is a closed polygon: `room.points = [[x,y], ...]` (clockwise, mm).
- **Persistence**: `Store` wraps `window.storage` (if present) or falls back to `localStorage`. `save()` debounces writes. `migrate(st)` upgrades older saved-state shapes on load — **when changing the shape of `S`, add a migration step here** rather than assuming fresh state. `S` itself is reassigned wholesale on load and on import; it lives in a module now and you cannot assign to an imported binding, so every such write goes through `setS(v)` (**[src/core/state.js](src/core/state.js)**), never a bare `S = …`.
- **Inventory tab**: organizes the same `S.inventory` used by Furniture mode, adding `item.folderId`/`item.manualTags` alongside the existing `item.tags` (the folder-inherited half — see `applyTags`/`reconcileTags`), plus top-level `S.itemFolders` (a folder tree with `tags:[]` materialized onto everything filed under it). Browsing is a folder tree (`#tree`) + grid (`#libContent`); editing an item's shape/color/count/etc. reuses the *same* `itemDialog(id)` modal as Furniture mode's "Add a thing" — the Inventory tab doesn't have its own item editor. Its own Export (`exportLibraryDialog`/`exportLibFolder`/`exportLibItems`) writes `{app, version, exported, inventory}`, the same shape `ITEM_SCHEMA.md` documents, so it round-trips through the app's main Import.
- **Marketplace tab**: two independent sources, both landing on the same `addMarketItemToInventory()` collision flow (see **Marketplaces** below):
  - **Subscriptions** (`S.marketSubs`): live `market.json` URLs per **[MARKET_SCHEMA.md](MARKET_SCHEMA.md)**. `subscribeMarket()`/`reloadMarketSub()`/`removeMarketSub()`/`fetchMarketItem()` fetch and validate `app`/`version` on every manifest, index shard, and item file. `marketIndexCache`/`marketItemCache` are in-memory `Map`s, never persisted — only the subscription record itself (`{id,url,name,version,itemURL}`) is saved.
  - Clicking a subscribed item opens `renderMarketItemPreview()` as a dialog (its "Add to library" defers `addMarketItemToInventory()` with `setTimeout`, so a collision dialog can open after the preview closes).
  - **Ad hoc listings** (`S.marketListings`/`S.marketFolders`): the older upload/paste-JSON/flat-link path, for sharing a one-off bundle without hosting a repo. Unrelated to the schema above.
- **Undo/redo**: room edits and furniture edits have **separate** history stacks (`roomHist`/`furnHist`), keyed per-layout. Use `commitRoom()`/`commitFurn()` after any change that should be undoable — don't mutate state without a corresponding commit.
- **Rendering** (the camera is **[src/canvas/view.js](src/canvas/view.js)**: `cv`, `ctx`, `view`, `sx`/`sy`/`wx`/`wy`, `snapPt`): `draw()` redraws everything to `<canvas id="cv">` every time state changes (immediate-mode, no diffing/virtual DOM). Side-panel HTML is rebuilt via `render*()` functions (`renderRoom`, `renderWalls`, `renderInv`, `renderSel`, etc.) that re-set `innerHTML` and re-bind listeners — follow this same pattern for new UI rather than introducing a framework.
- **Side panels**: left `#paneRoom` ("Plan") holds *lists* — rooms, then the items (Furniture mode) or walls/doors/structure (Room mode); right `#paneStuff` ("Properties") holds the *selection* first, then room properties / stock, then View settings. Sections meant for one mode carry `for-room` or `for-furn` and are hidden by `body[data-mode]` (set in `renderMode()`). Each `.pane` is a `.pane-head` rail plus a `.pane-body`; `applyPanes()` drives `S.leftOpen`/`S.rightOpen` and the `lc`/`rc` classes on `<main>`. Collapsing is desktop-only: under 900px the panes become `display:contents`, the canvas is sticky on top, and sections stack in the order set by `section[data-sec=…]{order}` in the narrow media query. Every `section` has a `.sec-head` (an `h2` that toggles collapse, plus optional `.sec-act` buttons such as the `+` that adds to that list) and a `data-sec` key persisted in `S.secClosed` — new sections need both.
- **Icons, dialogs, toasts** (**[src/ui/modal.js](src/ui/modal.js)**, **[src/ui/flash.js](src/ui/flash.js)**): icons are `<symbol>`s in the sprite at the top of `<body>`; render them with `svgI('name')` (no emoji). `openModal(title, html, okLabel, onOk, onMount, {danger:true})` styles a destructive action; `askConfirm()` always does. `flash()`/`libFlash()` stay up for `readTime(msg)`. `$(id)` and `esc(s)` — the two helpers every render path uses — are exported from `src/ui/modal.js` and `src/ui/panels.js` respectively.
- **Canvas colours** (**[src/canvas/draw.js](src/canvas/draw.js)**): `draw*()` functions read colours from `PAL()` (`CANVAS.light`/`CANVAS.dark`, following `prefers-color-scheme`), never literals. Only stage-side colours (background, walls, labels) differ in dark mode; selection/handles/warnings sit on the user's floor colour and keep light values. `savePlanImage()` (reached from the Export dialog) forces the light palette.
- **Double-click**: a wall opens `wallDialog(i)` — from the plan (canvas `dblclick` → `pickRoom`, Room mode only) or from a row in the Walls list. It is the same length/direction pair as the Selected panel, and it leans on `setWallLen`/`setWallAngle` returning false when `tryRoomEdit` rolls the change back, in which case the modal stays open over the flash message.
- **Row menus** (**[src/ui/menu.js](src/ui/menu.js)**, **[src/ui/inline-edit.js](src/ui/inline-edit.js)**): the `⋯` buttons (`moreBtn()`) open an anchored `openMenu(anchor, actions, title)` popup, not the modal. Actions that need more than one click (rename with a box, pick a folder, confirm a delete) open the modal *from* the menu. Renaming in place is `inlineEdit(el, value, done)`; because a row re-renders on a single click, click handlers on those rows go through `singleClick()`/`cancelSingleClick()` so a second click can become a double-click instead.
- **Reordering** (**[src/ui/dnd.js](src/ui/dnd.js)**): the layout tree and the inventory list use HTML5 drag-and-drop. `moveBefore(arr, movedId, targetId, after)` does the splice — folders and rooms live in separate arrays (`S.folders`, `S.layouts`), so a drop only reorders against its own kind and otherwise just reparents. `folderDescendant()` is the cycle guard.
- **Inventory scope**: `S.invScope` (`project` | `folder` | `room`, see `INV_SCOPES`) decides which rooms `usedCount()` counts, via `scopeLayouts()`. `folder` means the rooms sitting *directly* in the active room's folder — a subfolder is its own pool and never draws on the folder above it.
- **Modal dialogs** (**[src/ui/modal.js](src/ui/modal.js)**): implemented as a plain `<div>` (`#modal`), never `<dialog>` or `<form>` — the code comment explains both are blocked in sandboxed iframes this app may run in. Keep using `openModal()`/`closeModal()`.
- **Ids**: an inventory item's id is user-editable (Advanced, inside the edit dialog), so it is held to a URL/S3-safe character set by `idProblem()` — letters, digits, `! - _ . * ' ( )`, and `/` between path parts (no leading, trailing, or doubled slash). A slash reads like an S3 key: `ikea/kallax/4x2` and `ikea/kallax/2x4` sit in the same folder — both the Inventory tab's own folder tree (`rehomeItemId()` keeps an item's id filed under its folder path) and a subscribed marketplace's browse view (`marketPathChildren()` derives folders straight from id path segments, no separate folder list) use this convention. `retagItem()` is the only sanctioned way to change an id — it rewrites `placed[].itemId` in every layout *and* inside the `furnHist` snapshots, so an undo can't bring the old id back. `uniqueId(base, taken)` is the `-2`/`-3` collision suffix used by Duplicate and by import.
- **Export / import**: both go through a modal that picks what moves. `exportPayload()` writes a partial state — `{app, version, exported, folders, layouts, inventory}` plus the `PREF_KEYS` if settings were ticked — where any part may be empty; picking a room silently locks on the things standing in it so placements survive the trip. `readImport()` reads such a file back without assuming it is a whole project (a things-only file is valid), and `applyImport()` either replaces the project or merges: an item id that already exists here either wins ("keep mine", the rooms coming in re-point at yours) or is added beside it as `id-2`, a folder id that already exists **is** that folder, and placements whose thing resolves to nothing are dropped. `normLayout()`/`normItem()` are split out of `migrate()` so one room or one thing lifted out of a file gets the same clean-up — put new per-room/per-item shape fixes there, not in `migrate()` directly.
- **Blueprint import** (`bp*`, one block after `openingDialog`): traces a photo of a floor plan into rooms on a floor. Four stages in one `#modal` — choose a photo, crop, find the rooms, review — chained by the fact that an `onOk` returning `false` leaves the modal open, so each stage just replaces the body. `openModal` gained `opts.wide` and `opts.onClose` for this; `onClose` fires however the modal goes away (OK, Cancel, backdrop, Esc) and is where `bpDispose()` revokes the object URL. **The photo never touches `S`** — `save()` serialises the whole of `S` into localStorage, so megabytes of base64 there would break saving permanently and silently; it lives in the module-level `bpState` until commit, then it is dropped. Detection is a *proposal*: `bpState.proposal` is never mutated, corrections land in `bpState.edits`, and `bpRebuild()` derives the draft from scratch each time (changing the scale moves every room, so that has to stay idempotent over edits already made). `bpCleanPoly()` normalises winding, drops collinear vertices and merges sub-50mm edges **before** `polySimple()` — which is the only polygon gate; a weakened copy of it is what made an earlier attempt's rooms permanently uneditable. The import is not on any undo stack (the three stacks can't express creating a floor plus N rooms), so `bpLastImport` powers an explicit "Undo this import" instead. **Dividers** (`bpStampSplit`/`bpDeriveRegions`/`bpMarkSeams`) split one open region into two named rooms with no wall between them: a divider is a seed point plus an axis, stamped as a single pixel of barrier into a *copy* of the mask, after which the regions are re-derived by the same code the first pass ran — so merging two rooms is deleting a divider, and there is no polygon union anywhere in this file. Where a divider is proposed comes from `bpLabelBlocks()`, which finds the *positions* of name labels (S5 is what reads them) out of the small components the largest-component step discards. The resulting seam is cut out of the room's edge as an edge of its own and carries `wallOff`, which is what makes `floorSnapCandidates` report "Open through" and `floorEdgeDepths` draw nothing there.
- **Validation**: `validate(inst, poly)` / `insideRoom()` / `collides()` are the single source of truth for whether a piece of furniture placement is legal; reuse them rather than re-deriving overlap/bounds logic.
- **Measuring**: the canvas's Measure toggle (`#btnMeasure`, key `M`) sets `measureOn`, and while it's on `pointerdown` goes to `measurePointerDown()` instead of editing, in either mode. Measurements live on the layout as `l.measures = [{id, a, b}]`. Each end is an anchor `{k, id, part, n}`: `k` is `item|pillar|iwall|open|wall` (`id` is a room wall's *index*), and `part` is `corner`, `side` (with `n`), `whole`, or `swing` (a hinged door's `swingPoly()`, only pickable while door swings are shown). `measureObjs()` lists what can be measured and the anchors each offers. `anchorGeom()` turns an anchor into a point, segment or solid polygon, and `closestBetween()` gives the shortest distance between two of them. Ends are looked up on every draw, so a measurement follows what it joins; one whose end is missing is skipped rather than deleted (undo can bring it back), and `pruneMeasures()` drops it on load. Anything that gives things new ids (duplicating a room, importing one) must go through `remapMeasures()`. Measurements have no undo history.
- **Open state**: an inventory item may carry `item.open = {top,bottom,left,right}` (mm out past its own footprint, in the item's unrotated frame). `openPoly(inst,item)` is that footprint in world space and `openConflicts()` reports, per placed id, what it runs into. This is deliberately kept **out** of `validate()` — an open footprint never makes a placement illegal, it only warns — so don't fold it into the validity path.

## Conventions
- No semicolon-free style; ES2017-ish, `"use strict"`, no TypeScript. Keep new code consistent with the surrounding style.
- **Splitting `index.html` is Phase 3's job**, under move-only rules (see [`.claude/plans/refactor-split.md`](.claude/plans/refactor-split.md) — the mechanical recipe is in §4). Extraction goes **leaves first**: a `src/` module can import from another `src/` module, but nothing can import from `index.html`'s inline script, so a region may only move once everything it calls has moved. Unless you are the extraction agent for a region, keep new code in `index.html`.
- `function` declarations stay `function` declarations — never rewritten as `const f = () => {}`. ESM tolerates import cycles for hoisted function declarations but not for `const` bindings read during module evaluation, and this graph is dense and almost certainly cyclic.
- Angles: 0° points right, 90° points up (screen-plan convention), see `wallAngle`/`setWallAngle`.
